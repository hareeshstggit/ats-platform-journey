ATS Platform — Spec to Go-Live Journey

What this is: the real journey of an enterprise ATS built spec-first, end to end, by governed AI agents — what was built, how it was built, what pitfalls were hit along the way, how each one got captured and looped back into the rulebook so it can't quietly repeat, and why the whole thing stays a living process instead of a one-time setup. How an AI agent (or a new engineer) knows what to build, how to build it, why it's shaped the way it is, how it remembers what happened last week, how its own database evolves safely, and how the rulebook itself grows when something goes wrong.

Part 1 — The Map

Read this if you want to learn by opening the real files. Every section below names an actual file in this repo and tells you what to look for — it does not duplicate the file's content.

1. The governance stack

A governed codebase like this one has five distinct layers, each answering a different question. Confusing them is the single most common mistake newcomers make — e.g. putting business logic in an architecture doc, or business rules in code comments instead of a spec.

Layer Question it answers Where it lives
Spec What are we building, exactly? openspec/specs/<module>/spec.md
Standards What rules apply to everything, no exceptions? CLAUDE.md
Architecture Why is the system shaped this way? docs/ARCHITECTURE.md
Memory What happened, and where are we right now? memory/resume-pointer.md, docs/BACKLOG.md
Evolution How does the schema/system change without breaking prod? docs/SCHEMA_EVOLUTION.md, docs/SCHEMA_CHANGE.md

Read them in that order for any new module. Spec first — always. CLAUDE.md itself says so: "Build order is always spec-first: the spec.md is the contract, code implements it — never the reverse."

2. Layer by layer

2.1 Spec — openspec/specs/<module>/spec.md

Each business module (positions, applications, interviews, offers, security, …) has one spec file. Open openspec/specs/positions/spec.md and look for three things:

  • Acceptance criteria (AC-xxx) — the actual contract. If code and spec disagree, the code is wrong until proven otherwise.
  • Business rules (BR-xxx) — cross-cutting rules referenced from multiple endpoints.
  • Error codes and permissions per endpoint — read this before writing any code against the endpoint, not after.

2.2 Standards — CLAUDE.md

The file every agent reads before every task (its own first line says so). Skim its table of contents once. You'll see escalating tiers: ordinary code-quality rules, then binding process gates, then a small number of "no override" sections. Notice that most binding sections name the failure they prevent, right in the rule text.

2.3 Architecture — docs/ARCHITECTURE.md

Where CLAUDE.md says what the rules are, this file says why the system is shaped this way — the code map, module boundaries, the full expansion of the Engineering Mandate. Read this once per module you touch for the first time.

2.4 Memory — memory/resume-pointer.md + docs/BACKLOG.md

  • resume-pointer.md — chronological narrative, "you are here." Read this FIRST after any compaction or new session.
  • BACKLOG.md — query-free current-state snapshot. No narrative, just what's open right now. Carries its own binding rule at the top: update inline, same commit.

The trap to notice: these files diverge across open, unmerged git branches — each branch's copy is a snapshot from whenever it forked. Look for a line in this repo's own BACKLOG.md acknowledging exactly that, written live during a real multi-branch session — a governance system that names its own blind spots is more trustworthy than one that pretends not to have any.

2.5 Evolution — docs/SCHEMA_EVOLUTION.md + docs/SCHEMA_CHANGE.md

  • SCHEMA_EVOLUTION.md — a decision tree, consulted before any new data is stored: JSONB → lookup_values → custom_field_definitions → tags → only then a real column/table.
  • SCHEMA_CHANGE.md — the permanent log of every schema change ever made, with the why, not just the current shape.

Find the backfill mandate in CLAUDE.md's schema section — it names a real incident. Part 2 tells that story in full if you'd rather read it than dig for it.

3. Who's actually driving — the orchestration model

There is no separate orchestrator agent. The main-loop session — human-supervised — is the orchestrator. Find CLAUDE.md's "Subagents" section and read the pipeline it states directly: backend-engineer → unit-test-engineer → functional-test-engineer → integration-test-engineer → principal-reviewer → human approves merge. "Human-supervised" governs decisions — approvals, scope, priority, design calls, new rules from failures — not the work itself: once dispatched, each agent runs its slice end to end, autonomously. Part 2 §8.1 unpacks this fully.

Where each subagent's real contract lives: .claude/agents/*.md — one file per named subagent. Open .claude/agents/principal-reviewer.md and check its frontmatter (model:, effort:) against what CLAUDE.md's Model Tier mandate says that role should be pinned to. They should match.

Three enforcement layers, not one: the main loop's own compliance, principal-reviewer independently re-checking the actual diff (not trusting self-report), and the human's final merge approval. Notice that two of CLAUDE.md's rules state they cannot be overridden by any number of user requests, ever — only an edit to the file itself changes them. Find both. Ask yourself why those two, specifically, earned that tier.

4. Try it yourself

  1. Open CLAUDE.md and find the gate that would block a bug fix from going straight from "verified in browser" to "ready to merge" with no review.
  2. Open docs/BACKLOG.md and find the maintenance rule stating when it's supposed to be updated.
  3. Pick any module's spec.md. Find one acceptance criterion, then find the code file that implements it, and confirm the code actually does what the AC says.
  4. Compare .claude/agents/principal-reviewer.md's model/effort pinning against CLAUDE.md's Model Tier mandate. They should match — a mismatch would itself be a defect this system is designed to catch.
  5. Find a binding rule in CLAUDE.md and identify what incident it cites. If it doesn't cite one, ask why not.

Part 2 — The Manual

Read this if you'd rather have every mechanic explained inline, with no other file to open. This part is self-contained.

1. Why a governed codebase looks different

A single AI coding session, working alone, for one afternoon, doesn't need much governance — the human is watching every line. An AI agentic system — one that runs across days, compactions, multiple specialized subagents, and dozens of merged PRs — falls apart without it, for three specific reasons:

  1. Context doesn't survive by default. An AI's working memory resets between sessions. Without a deliberate mechanism, every new session re-derives (or mis-derives) what's already been decided.
  2. Consistency doesn't survive scale by default. One agent's "reasonable judgment call" on Monday becomes a different agent's "reasonable judgment call" on Thursday. Without a shared rulebook, the same class of bug gets re-introduced indefinitely.
  3. Trust doesn't survive delegation by default. The moment work is delegated to a specialist (a "sub-agent"), someone has to check its output against the same standard a human reviewer would apply — or delegation just means unverified work ships faster.

This repository solves all three with the same tool: durable, git-tracked files that are read back into context automatically, and a review gate that checks work against them independently. Everything in this part is a variation on that one idea.

2. Project organization

At the top level, the repository separates into five kinds of thing:

ats-platform-project/
├── backend/            # FastAPI app — router → service → repository layers
├── frontend/            # Next.js app — components, hooks, API client
├── openspec/            # Specs: the contract for every module (source of truth)
├── docs/                # Living documentation: architecture, schema, backlog, guides
├── .claude/             # The governance machinery itself
│   ├── agents/          # One file per named subagent — its actual contract
│   ├── rules/            # Domain guardrails loaded globally (not per-file)
│   └── settings.json     # Hooks — e.g. auto-loading docs/BACKLOG.md every session
├── memory/              # Durable "you are here" — survives compaction/new sessions
└── CLAUDE.md            # The rulebook. Read before every task, no exceptions.

The organizing principle: code lives where its layer says it should (backend/app/modules/<name>/{router,service,repository,models,schemas}.py), and everything that ISN'T code — decisions, rules, history, contracts — lives in a predictable, git-tracked location too. Nothing important is allowed to exist only in someone's head or in a chat transcript that gets discarded.

A new module always follows the same skeleton:

backend/app/modules/<name>/
├── router.py       # HTTP only — validate input, call service, shape response
├── service.py      # ALL business logic — no raw SQL, no HTTP concepts
├── repository.py   # ALL DB access — no business logic, returns ORM objects
├── models.py       # SQLAlchemy ORM models only
├── schemas.py      # Pydantic v2 request/response schemas only
├── exceptions.py   # One custom exception hierarchy per module
└── tests/          # Unit + functional tests, mirroring the same layers

This strict layering is itself a rule from CLAUDE.md (§ "Architecture"), and it's enforced two ways: principal-reviewer checks for layering violations on every review, and the codebase's own history has caught real violations of it — e.g. a module importing another module's Repository class directly instead of going through its Service, discovered during a routine decomposition review and logged in docs/BACKLOG.md as a tracked architecture defect rather than silently left alone.

3. The Standards Layer — CLAUDE.md

CLAUDE.md is the single most important file in the repository. Its own first line states its job: "Claude Code reads this before EVERY task. All generated code complies." It is re-injected into an agent's context at the start of every conversation turn — not something an agent has to remember to open.

3.1 What's actually inside it

Reading top to bottom, CLAUDE.md moves through increasing levels of bindingness:

Baseline standards — the kind of rule every serious codebase has, whether or not it's AI-authored: type hints on every function, docstrings in a fixed 2–3 line format, a 40-line function cap and 300-line file cap, structlog instead of print(), no PII in logs, 80% minimum test coverage, soft deletes instead of hard deletes, optimistic concurrency on versioned updates, idempotency keys on mutating endpoints.

The Engineering Mandate — a compressed statement of the project's actual philosophy: "Write the minimum code that makes the intended function run correctly and efficiently — not one line more." No speculative features, no unused parameters, no "might need later" abstractions. This isn't a style preference — it's stated as a hard contract, and the authoritative expansion lives in docs/ARCHITECTURE.md.

Process gates — this is where the file stops being generic and becomes specific to this project's actual failure history. Each gate exists because something concrete went wrong once:

  • Quality Gate Rules 1–5 — clarify silences before building (not after), verify async outcomes not just enqueue confirmations, mandatory set_rls_context on RLS-protected Celery tasks, UI golden-path verification before calling anything "done," mandatory functional-test cleanup with an exact soft-delete-vs-hard-delete table per entity type.
  • Regression Prevention Gates 1–5 — run unit tests before spawning any other agent; fix user-visible tech debt next session, not "eventually"; read the spec before touching any status/enum/transition map; route small fixes to a cheap, scope-limited agent instead of a heavyweight one; and Gate 5 — every bug fix, regardless of size, goes through investigate → fix → review, with no override mechanism at all.
  • Model Tier & CI Independence mandate — pins the senior review role to a stronger model tier permanently, and requires CI jobs to run as independent parallel jobs (never sequential steps where one early failure masks everything behind it).

"No override" vs. "3-request override" — two distinct resistance tiers. Some gates can be lifted if a user asks to skip them three times in a row, consecutively — with the agent naming the gate and pushing back on the first two asks. Two gates cannot be lifted at all, by any number of requests: the only way to change them is editing CLAUDE.md itself. The calibration is deliberate — softer gates protect against carelessness; the two hard gates protect against a specific, expensive failure that already happened once.

3.2 Why this structure works

The reason this isn't just a style guide nobody reads: every binding section states the failure it prevents, in the rule text itself. A rule with no stated incident reads as a guess. A rule with a named incident reads as a fix — and is far harder to rationalize skipping "just this once," because the cost of skipping it is written down right there.

4. The Architecture Layer — docs/ARCHITECTURE.md

If CLAUDE.md is the compressed rulebook, docs/ARCHITECTURE.md is the expansion — the "why," not just the "what." It carries:

  • The code map — which directory owns which responsibility, and the boundaries between modules.
  • The full Engineering Mandate — CLAUDE.md's "minimal, optimized, modular, maintainable" contract, expanded with the actual SLOs a real hot path is measured against (this project's stated target: 200+ concurrent users, no perceptible screen-response slowdown).
  • Cross-module boundaries — the rule that inter-module calls must go through the other module's service interface, never its repository directly. This is checked by principal-reviewer on every review, and violations of it are tracked as real, named tech debt in docs/BACKLOG.md when found — not silently fixed and forgotten, because a fix without a record just means the next person re-discovers the same problem from scratch.

Read this file once per module, the first time you touch it — not every session. Unlike CLAUDE.md (universal, re-read constantly) and specs (per-feature, read before building), architecture context changes slowly and is meant to be internalized, not re-verified every turn.

5. The Context System — staying current, never stale

This is the part that has no equivalent in a single-session coding tool, because a single session doesn't need it. An agentic system that spans days needs an answer to: how does a brand-new session, with zero memory of anything, know what's already true?

The answer is a deliberate three-file split, each with a distinct job:

5.1 memory/resume-pointer.md — the chronological narrative

This is the first file read after any compaction or new session, before even the specs. It answers "what happened, when, and why" — a running log of resolved work, in-progress work, and the exact state something was left in. It is git-tracked, which matters: a chat-only memory disappears with a cleared profile or a new machine; this file survives both, because it's just a file in the repository like any other.

The file states its own failure mode explicitly: if an agent can't restore context and this file is missing or stale, that itself is the bug to report — the file's own maintenance is treated as load-bearing infrastructure, not a nice-to-have.

5.2 docs/BACKLOG.md — the query-free current-state snapshot

Where resume-pointer.md is a story, this file is a snapshot — no dates, no narrative, just what's true right now: the active execution queue, PRs pending merge, tech debt by category, deferred features. Its own binding rule, stated at the top of the file: update this file inline, in the same commit, whenever an item changes status. Not "eventually" — the same commit.

This file is important enough that this project wired a SessionStart hook (in .claude/settings.json) that loads it automatically at the start of every session, so a human opening the project never has to ask "what's the state of things?" — it's already in front of them.

5.3 Auto-memory — durable facts about the collaboration itself

Separate from both of the above, an agentic assistant can maintain its own persistent memory of the user and the working relationship — preferences, corrections, confirmed-good judgment calls, project facts that aren't really "backlog" items. This is deliberately kept out of BACKLOG.md/resume-pointer.md, because conflating "what's the state of the project" with "what have I learned about how this person likes to work" produces a document that's useless for both purposes.

5.4 Why staleness is a known, named risk — not a silent one

The most honest thing about this system: it doesn't claim to be immune to drift. When multiple branches are open simultaneously, each branch's copy of docs/BACKLOG.md is a snapshot from whenever it forked — edits on one branch don't appear on another until merge. This repository's own backlog carries a line acknowledging exactly this, written live during a real session with four branches open at once, rather than pretending the problem doesn't exist. A governance system that never admits its own blind spots is more dangerous than one that names them and tells you when to reconcile.

6. Database schema evolution

Schema changes are the single highest-blast-radius kind of change a codebase makes — they're hard to reverse, and a mistake can silently corrupt data rather than just crash. This project handles it with a decision tree plus a permanent log.

6.1 docs/SCHEMA_EVOLUTION.md — consulted before every new kind of data

The rule: before storing any new attribute, walk this order, cheapest-safe-option first, and only escalate when the cheaper option genuinely doesn't fit:

  1. Metadata JSONB on the existing entity (cheapest, no migration).
  2. A lookup-values table (for a small, evolving set of categorical options).
  3. Custom field definitions (for admin-configurable, per-tenant fields).
  4. Tags (for loose, many-to-many categorization).
  5. A real column or table — only for data that's hot-queried, indexed, or genuinely relational. Never an EAV (entity-attribute-value) pattern.

This exists specifically to stop the slow accumulation of one-off nullable columns added for every feature request — a real, common failure mode in long-lived schemas.

6.2 The additive-only migration rule

Every schema change is backward-compatible only: new columns nullable or defaulted; existing indexes/constraints/RLS preserved; nothing populated is dropped, renamed, or retyped in the same release the running code depends on it. Removing something old happens in phases — add new, backfill, switch reads/writes, drop old later, never all at once. Every migration is also reversible — a real downgrade, not a stub — and validated against existing data both directions before it ships.

6.3 docs/SCHEMA_CHANGE.md — the permanent, structured log

Every schema change, no exceptions, gets one entry: date, baseline, author, the trigger (what feature or fix required it), the change type, which storage mechanism was chosen from the §6.1 decision tree (and why, if a real column was needed), the migration's revision id, a backward-compatibility/rollback note, and the linked spec/PR. This is the answer to a question a live database schema can never answer on its own: why does this column exist, and was it deliberate?

6.4 The backfill mandate — a rule earned by a real incident

A subtle trap this project actually hit: a migration can be "technically true" saying "no existing rows affected, backfills to NULL" while being functionally wrong, because the value already existed elsewhere (a status history table, a related entity) and just wasn't backfilled — NULL for "already decided before the column existed" is indistinguishable from NULL for "never decided," so any feature reading that column misbehaves silently for every pre-existing row.

Rule this incident produced: every such migration must explicitly (a) write an idempotent backfill deriving the value from its authoritative source wherever unambiguous, or (b) document why none was possible — silence is not an acceptable default, a reviewer must affirmatively confirm one was considered.

8. The orchestration model

8.1 There is no meta-orchestrator agent

The most common misconception about multi-agent systems: that there's a tower of agents, with something at the top orchestrating everything below it. That's not what this repository does. The main-loop session — a human-supervised Claude Code conversation — is the orchestrator. It reads CLAUDE.md's stated pipeline:

backend-engineer → unit-test-engineer → functional-test-engineer →
integration-test-engineer → principal-reviewer → human approves merge

...and dispatches specialist subagents accordingly, every module, every session.

"Human-supervised" does not mean "hand-held." Once dispatched, a subagent runs its assigned slice — UX/UI, feature build, unit tests, functional tests, review — end to end, autonomously, no prompt-by-prompt steering inside that work. A backend-engineer run doesn't pause mid-task for a human to confirm the next line; it builds the whole slice and reports back. What the human-in-the-loop conversation actually governs is a narrower set of decision points, not the execution itself: approvals (merging a reviewed PR — always the human's last step, never delegated); scope confirmations (what a feature means, before agents are dispatched — Rule 1 in §9: clarify before building, never after); priority decisions (what's next, what waits); architecture/ design judgment calls a spec doesn't already settle; confirming a genuine fork an agent or the orchestrator surfaces (the orchestrator doesn't guess); and rule creation from failure — a new binding mandate gets authored into CLAUDE.md here (§9), after which both orchestrator and every subagent are bound by it autonomously, with no turn-by-turn reminder needed.

Dispatch, execution, and reporting are autonomous. Direction, judgment, and final sign-off are the human's. No separate process watches the main loop do this — the discipline is CLAUDE.md re-injected every turn, read before every dispatch.

8.2 Where each subagent's actual contract lives

CLAUDE.md's roster is a pointer. The binding contract — system prompt, tools, model, default effort — lives in one file per subagent under .claude/agents/. File names and name: frontmatter are load-bearing: principal-reviewer.md's name: principal-reviewer must match the string CLAUDE.md uses, and its model: opus / effort: high must agree with the Model Tier mandate's independent statement of the same rule — two files, one binding fact, checkable by inspection.

Not every agent in a session is project-defined this way — some come from a separately installed plugin (cheap, general-purpose lookups/edits/diff-review, not domain-specific). Knowing which agents are this project's binding contracts vs. general tooling matters when reasoning about why an agent behaved a certain way.

8.3 The three-layer enforcement model

No single mechanism guarantees the rulebook is followed. Three independent layers do:

  1. Self-enforcement by the main loop. It follows CLAUDE.md because the file is re-injected every turn and the main loop is instructed to treat project instructions as binding, overriding its own generic defaults.
  2. principal-reviewer as the actual gate. This is the layer that matters most in practice — it independently re-reads the relevant spec and CLAUDE.md, and runs its own mandate-compliance checklist against the real diff, not against what an upstream agent claims it did. In this project's real history, review rounds routinely catch things the main loop or an implementing agent missed: a doc left stale, a test that would silently pass even if the fix it's meant to guard were reverted, a spec line that needed syncing to match new observable behavior. Each of those is closed in a follow-up round before the change is allowed to proceed — which is the entire point of having an independent reviewer instead of trusting self-report.
  3. Human final approval. Regardless of how clean the reviewer's verdict is, merge approval is a separate, explicit human step, every time.

8.4 The override-resistance design

Two of this project's rules state, in their own text, that they cannot be lifted by any number of user requests in any session — only an edit to CLAUDE.md itself changes them. Other rules use a softer "three consecutive requests" pattern: the agent must name the gate and push back on the first two asks, and only lift it, scoped to that one instance, on the third. This tiering is deliberate: the hard-override-proof rules protect against the specific, already-expensive failures named in §9 below; the softer rules protect against ordinary carelessness, where a small amount of friction is enough.

8.5 Model + effort routing — a lever picked per task type, not per session

Two independent knobs, both pinned per-agent in .claude/agents/*.md frontmatter, never left to inherit from whatever the main loop happens to be running:

Task type Agent Model Effort
Backend API/service/DB backend-engineer sonnet high
Frontend/UI ux-ui-engineer sonnet high
Unit tests (mocked) unit-test-engineer sonnet medium
Functional/integration tests functional-test-engineer, integration-test-engineer sonnet medium
Merge-readiness review (the one chokepoint) principal-reviewer opus high
On-demand deep dive (failure modes, DR) principal-reliability-engineer opus xhigh
On-demand deep dive (perf, query plans) principal-performance-auditor opus xhigh
"Where is X / what calls Y" lookups cavecrew-investigator cheap fixed tier low
Bounded 1–2 file edit cavecrew-builder cheap fixed tier low

Why only 3 of 8 run Opus: principal-reviewer is the single gate every change passes through exactly once; the two specialists are on-demand for the highest blast-radius categories only. Everywhere else, Sonnet's ceiling was never the constraint — paying Opus rates there buys no quality the pipeline doesn't already get structurally. Max reasoning effort is reserved the same way: never a standing default, only for a run that genuinely needs it (a security-sensitive review, for instance).

9. The mandate lifecycle — how rules are born

This is the section worth studying most closely if your goal is to build your own agentic system's rulebook, not just operate this one.

9.1 The pattern

Every binding section of CLAUDE.md in this project follows the same shape:

Name the incident. State the rule that closes it. Cite what would have caught it earlier, if anything would have.

A rule with no stated incident reads as a guess about what might go wrong. A rule with a named incident reads as a fix for something that did. The difference matters enormously in practice — a guess is easy to rationalize skipping under time pressure; a named, expensive incident is much harder to wave away, because the cost is written down in the rule itself, not left to the reader's imagination.

9.2 Three real examples from this repository

Gate 5 — the full subagent pipeline, no override. Born from a specific session where three consecutive bug fixes were made entirely in the main loop — no dispatched root-cause investigation, no reviewed implementation, no sign-off before merge — and the resulting cost escalation from the rework this caused is what produced the rule. The rule text states the date and the exact failure mode, not an abstracted version of it.

The Model Tier & CI Independence mandate. Born from a status review that discovered two separate things going wrong for structural reasons, not because anyone was careless: (a) a senior review role needed multiple rounds to close out even a single change, even running on a capable model — suggesting the model tier itself wasn't matched to the stakes of that role; and (b) a CI pipeline had, for the entire life of the repository, run linting as the first sequential step of one job — meaning type-checking and the full test suite had never run once, because the first check never failed until that specific review. Real errors had been silently hidden the entire time, not because of one bad commit, but because of how the pipeline itself was shaped. The mandate closes both: a permanent model-tier split for the highest-stakes roles, and a rule that CI jobs must run as independent, parallel jobs — never sequential steps where one early failure masks everything behind it.

The backfill mandate — full incident and rule in §6.4 above. Same pattern: a technically-true migration docstring, a silently-misbehaving shipped feature, a rule requiring an explicit backfill-or-justify decision instead of silence.

The Dependency-Mapping & Live-EXPLAIN-Verification rules (Rules 6-7, 2026-07-31). Born from a single feature — reshaping an interview-pipeline reporting endpoint to show all interview levels at once instead of one at a time — that took three separate rounds of user clarification to scope, then three more rounds of principal-reviewer findings to build correctly. The user asked directly for a retrospective, naming this "the 2nd or 3rd time Claude has struggled to get to root cause" and asking whether the dependencies and integration points had been properly mapped up front. The honest answer was no, for two distinct structural reasons — not carelessness: (a) the change's design.md mapped implementation files but never asked "what UI entry point reaches this," "what else consumes this response shape," or "what invariant does the current row grain silently guarantee" — each gap surfaced only as an expensive review-round finding, never at design time; (b) a review round found a "fixed" performance defect — a redundant correlated subquery — had NOT actually been fixed, despite every test passing and the code and docs both claiming otherwise; only a live EXPLAIN (ANALYZE, BUFFERS) revealed the duplicate query-plan node still there. Two rules closed the two gaps: Rule 6 makes the dependency/integration-point mapping above a required section of design.md itself, completed before any build is dispatched; Rule 7 requires the building agent — not just the reviewer — to run a live EXPLAIN at build time for any change touching aggregation, ordering, or pagination grain, because passing tests confirm correct results, never correct query plans.

9.3 What to take from this if you're building your own system

When you write your own agentic project's rulebook:

  • Write the incident into the rule itself, not a separate changelog nobody re-reads.
  • Calibrate override resistance to the cost of the failure — "no override, ever" only for genuinely expensive, already-happened-once failures; softer friction elsewhere.
  • Let an independent reviewer check compliance against the actual diff, never trust the implementing agent's self-report.
  • Name the rule after what it prevents ("Gate 5: full subagent pipeline"), not a number — memorable enough to survive a rushed Friday afternoon.

10. A complete worked example

Trace one real class of change through every layer described above, in order:

  1. A tech-debt item is diagnosed. Root cause is confirmed against the actual spec acceptance criterion — not assumed from reading the code alone. If the code and the spec disagree, the working assumption is that the code is wrong, until proven otherwise by re-reading the spec's exact wording.
  2. The fix is scoped to the correct architectural layer — a query-ordering defect belongs in the repository, not the service; a missing test belongs in the test suite, not a code comment explaining why it's fine to skip.
  3. Unit tests run before any other agent is dispatched (Regression Prevention Gate
    1. — catching the majority of regressions in seconds, before a more expensive review pass is even requested.
  4. principal-reviewer runs a full mandate-compliance checklist against the actual diff. In this project's real history, this step is rarely a rubber stamp on the first pass — it routinely finds something concrete: a documentation file that wasn't updated in the same commit as the code change it describes, a test that would pass even if the exact fix it's supposed to guard were silently reverted, a spec line that needed a one-sentence update to match new, now-observable behavior.
  5. Findings are remediated and re-reviewed — as many rounds as it takes, each one narrower than the last, until the reviewer's checklist has no remaining failing dimension.
  6. A pull request is raised carrying a provenance block — which agent implemented the change, and which reviewer signed off, with the verdict recorded as a machine-readable commit trailer, not just prose in a PR description.
  7. docs/BACKLOG.md is updated in the same change that closes the tracked item — so the very next session, cold, with zero memory of any of the above, can read one file and know the item is done, not still open.
  8. A human approves the merge, separately from and after the reviewer's verdict.

Every single step above is a real, binding, named rule from CLAUDE.md — none of it is informal convention. That's the entire difference between a governed agentic codebase and an ungoverned one: not that mistakes never happen, but that every mistake that has happened left behind a rule that makes the same mistake structurally harder to repeat.

11. Token-optimized development — a binding discipline, not a suggestion

Compute cost is real money against real value delivered. This project treats it as a governed discipline with its own living playbook (docs/TOKEN_OPTIMIZATION_PRACTICE.md, excerpted in §3.10 below), not an occasional cost-cutting pass.

How it evolved. Started (2026-06-18) as a 7-discipline playbook after one $100 session prompted a post-build cost review. Grew, dated entry by dated entry, every time a real session surfaced a new waste pattern: model-availability failures wasting ~$15–20 mid-run (→ verify-once-per-session rule), a review needing 3 rounds because model tier didn't match the stakes of the role (→ the two-tier Opus/Sonnet roster), a playbook section caught silently drifting one commit behind its own binding rule (→ the "report what you applied, every task, no exceptions" showcase rule). By 2026-07-24 the core disciplines — right agent for the task, spec pre-read before building, cost alert before and after every task, no size carve-out — were promoted from "playbook advice" into CLAUDE.md itself, enforced under the same no-override class as Gate 5.

Where caveman and superpowers fit in. Neither is this project's own invention — both are installed tooling this project leans on:

  • Caveman mode strips filler prose (articles, hedging, pleasantries) from every response automatically, persisting across the whole session — measured ~15–25% output-token reduction with zero loss of technical substance. It's why this very document reads terser once you notice it.
  • Superpowers' skill-invocation discipline forces a fork before any build: if a spec already exists, go straight to dispatching agents against it; if none exists, brainstorm and propose one first (/opsx:propose) rather than building on an assumption that turns into a expensive rework cycle later. This is the upstream fix for the single costliest failure mode measured on this project: a preventable review-rejection cycle, which costs as much as the original build.

Both are orthogonal to the ATS-specific playbook above — one compresses prose, the other compresses wasted exploration — and both are active by default, not opt-in per task.

The new independent lint job's first real run separately surfaced 804 previously-invisible findings from an unpinned tool version, within hours. Both are cited as direct, same-day proof that the structural fix works, not a hoped-for improvement.

13. Glossary

Binding rule — a CLAUDE.md rule stated as non-optional, typically citing the incident that produced it.

Gate — a binding rule that blocks progression to the next step until satisfied (e.g., unit tests must pass before another agent is dispatched).

Mandate — a binding rule broad enough to span multiple gates or a whole category of work (e.g., the Model Tier & CI Independence mandate).

Override resistance — how hard a rule is to bypass: "3-request" (soft, can be lifted after three consecutive explicit asks) vs. "no override" (hard, changeable only by editing CLAUDE.md itself).

Orchestrator — the human-supervised main-loop session that reads CLAUDE.md and dispatches subagents accordingly. Not a separate agent.

Subagent — a specialist agent dispatched by the orchestrator for one bounded task (e.g., backend-engineer, principal-reviewer). Its real contract lives in .claude/agents/<name>.md.

Review gate — the specific role (principal-reviewer in this project) that independently re-checks work against the rulebook before human merge approval, rather than trusting the implementing agent's self-report.

Living document — a file whose binding rule requires it to be updated in the same commit as the change it describes, so it never drifts out of sync with the code (e.g., docs/BACKLOG.md, docs/SCHEMA_CHANGE.md).

Spec-first — the discipline that the spec (openspec/specs/<module>/spec.md) is written or updated before code changes, never the reverse — the spec is the contract, the code implements it.

AI compute cost scales with output tokens (~5x the cost of input tokens).

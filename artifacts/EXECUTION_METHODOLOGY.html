ATS Platform — Execution Methodology

Last updated: 2026-07-24 · Living document — update in the same PR as any agent/CI/mandate change (see docs/TOKEN_OPTIMIZATION_PRACTICE.md's living-doc rule) · Source: PR #191/#192/#193 · Author: Claude Code (agent), reviewed by principal-reviewer

This document records what changed in how work on the ATS Platform gets executed — the agent pipeline, the model/effort tiering behind it, and the new binding project rules — following a same-day review of repeated late-cycle bug discovery and a CI-visibility gap that had existed since the repository's creation.

1. Why this changed

Two structural gaps were found on 2026-07-23/24, neither fixed by "try harder":

  • CI masking. backend-ci.yml ran ruff → mypy → pytest as sequential steps in one job. The first failing step stopped the job — so mypy and the full pytest suite had never run to completion, once, in the repo's entire history. This silently hid 52 mypy errors and 18 Postgres/Redis-dependent test failures until a lint cleanup accidentally let the job run past ruff for the first time.
  • Review depth at the single chokepoint. principal-reviewer — the one gate every change passes through before merge — took 3 rounds to close a single change (a missed endpoint, then a missed spec-sync update) even at high effort, because it was on the same model tier as every other agent in the roster, with no tier reserved for the highest-leverage review/specialist work.

2. Workflow: before → now

AspectBeforeNow
Backend CI (backend-ci.yml) One job, lint-type-test: ruff → mypy → pytest as sequential steps. An early failure silently masked every later check's result. NEW Four independent parallel jobs: lint, dependency-drift, typecheck, test. Each reports its own pass/fail; no needs: dependency between them.
Frontend CI (frontend-ci.yml) One job, lint-typecheck-test: lint → typecheck → test → build sequential, plus a separate e2e job. NEW Independent lint, typecheck, component-test, build jobs; e2e unchanged.
Dependency-drift detection None. A package installed locally outside the tracked dependency list stayed invisible to CI until CI itself broke on it (the psycopg2-binary incident). NEW Mandatory deptry job on every backend CI run — fails the build if a first-party module imports an undeclared package.
Tool-version drift Dev tools declared as open floors (e.g. ruff>=0.4) with no upper bound — CI could silently resolve a newer version than any developer had tested against. NEW Precedent set (via the ruff 0.16.0 incident, 2026-07-24): pin correctness-gate tooling to an exact, verified-clean version, matching the existing bcrypt==4.1.3 pattern.
Cost visibility Cost alerts only required for "non-trivial" tasks; no standard after-the-fact actual-cost report. NEW [COST ALERT] before and after every task, no size carve-out — plus a mandatory statement of which specific token-optimization practice was applied and how it saved cost, for every task.
Model/effort tiering Single-tier: every agent on Sonnet, effort varied by role. NEW Two-tier: 3 chokepoint/specialist roles on Opus (fixed, no per-task re-evaluation); the rest stay on Sonnet.

2b. What stayed the same

The router → service → repository layering, the OpenSpec spec-first workflow, the Quality Gate rules (async-outcome verification, RLS context in Celery tasks, functional-test cleanup), Gates 1–4 and their 3-request override rule, and Gate 5's 3-stage bug-fix pipeline (cavecrew-investigator → fix agent → principal-reviewer) are unchanged. This update extends the existing governance model — it does not replace it.

Why these 3, and no others

principal-reviewer is the single merge chokepoint every change passes through exactly once — the highest-leverage point to spend more on. principal-reliability-engineer and principal-performance-auditor are on-demand specialists engaged only for the highest blast-radius categories (data loss, broken recoverability, perf regressions at 200+ concurrent users). In both cases the cost delta (roughly 1.7–2.5× Sonnet, depending on Sonnet's intro vs. standard pricing window) is trivial against the cost of a defect that gate or specialist was supposed to catch and didn't. The remaining agents run high-volume, well-scoped, mechanical-to- moderate judgment work where Sonnet's ceiling was never the constraint.

4. New binding mandates added

Model tier & CI independence mandate (NO OVERRIDE)

Added 2026-07-24, same enforcement class as the pre-existing Gate 5. Fixes the two-tier model roster in place by agent file name (load-bearing, not cosmetic); requires all CI jobs to be independent, parallel jobs with no needs: dependency between checks; makes dependency-drift detection (deptry or equivalent) mandatory in backend CI. Cannot be lifted by any number of user requests in any session — the only way to change it is to edit CLAUDE.md directly.

Cost alerts — before and after every task (NO OVERRIDE)

Supersedes the old "simple tasks: no alert" carve-out. Every task — regardless of size — states a [COST ALERT] estimate before starting and the actual cost/tokens spent after finishing, flagging any overrun beyond ~2× the estimate.

Token-optimization practice showcase (NO OVERRIDE)

After completing any task, name the specific docs/TOKEN_OPTIMIZATION_PRACTICE.md practice(s) applied and state concretely how each reduced this task's actual spend — not a generic restatement of the practice. An explicit "N/A" is required if none meaningfully applied; silence is non-compliant.

All three mandates sit in the same enforcement class as Gate 5: not subject to the 3-request override rule that governs Gates 1–4, and not waivable by any in-session user request, however explicit. Changing them requires editing CLAUDE.md itself.

5. First real-world validation (same day)

PR #193 (the change that introduced this update) dogfooded its own new gate: the retiered principal-reviewer reviewed its own creation and caught 4 genuine defects across two rounds (a duplicate doc-section heading, a stale cost-alert rule contradicting the same PR's own change, a missing playbook entry, and — the sharpest finding — a dependency-drift check sequenced after lint in the same job, reproducing the exact "one failure masks another" pattern the whole mandate exists to close). Separately, the new independent lint job's first real CI run surfaced a genuine ruff-version-drift bug within hours of merging (804 previously-invisible lint findings from an unpinned tool version) — direct, same-day proof that job independence surfaces information a combined job would have kept hidden.
